# Windows 11 x64 完整安装包 SPEC

日期：2026-09-24。状态：用户已确认，开发中；尚无 Windows 可下载版本。承接现有 Native/安装器源码；本增量扩展阶段 C 原先排除 Windows 的范围。

## 已确认的用户选择

- 仅 Windows 11 x64（Intel / AMD），首轮不覆盖 Windows 10 或 ARM。
- 同事提供 Windows 11 x64 真机并配合验收，可以自行安装软件。
- 完整安装包，内置运行环境和分析依赖；普通用户不配置开发环境或输入终端命令。
- 优先当前用户安装，不要求管理员权限。

## Problem Statement（问题陈述）

现有 GitHub 下载包仅适用于 macOS Apple Silicon。Windows 用户按文档执行 shasum 和 start.command 无法完成安装；更换校验命令不能解决底层平台不兼容。Chrome 扩展只是采集入口，必须有 Windows 版本地配套程序才能实现完整分析。下载入口和安装文档还需清晰区分平台。

源码核对发现：打包脚本、payload 清单、AppKit 安装界面、Native 注册位置、Python 启动路径、系统钥匙串和浏览器启动方式依赖 macOS；Rust 启动器中的 node.exe 分支不足以证明 Windows 可用。

## Proposed Solution（方案描述）

1. 共用现有 Chrome 扩展、工作台和分析协议，新增 Windows 平台适配，不复制一套独立产品。
2. 提供 x64 图形安装包，内置 Node、Python、图像分析依赖与 Native 启动器。普通用户无需另装 Python/Node、运行 shasum、手工编辑注册表或复制令牌。
3. 按当前用户安装到 LocalAppData 下受控程序目录，项目数据与程序目录分离。安装器执行完整性检查；SHA-256 同时供发布方和高级用户核验，不作为普通用户手工操作前提。哈希校验不冒充发布者身份签名。
4. Native Messaging 在 HKCU 注册，仅允许明确配对的扩展 ID；正式商店条目 ID 为 dmkfgmpbomjjhalgnfhcpalobdnklchh。商店可安装前可用解压扩展进行内部验收，但必须明确区分开发 ID，不能扩大为来源通配符。
5. 点击扩展启动或复用服务，使用一次性票据打开工作台；日常无控制台窗口、无令牌输入。服务继续只监听本机回环地址，保留认证、CSRF、并发启动锁、空闲退出及休眠恢复保护。
6. 安装、更新、修复与保留数据卸载有图形入口；更新失败保留可恢复的原程序。同结构回退可复用既有逻辑，但不得承诺任意数据库版本降级。
7. AI/Figma 凭据引入 Windows 系统保护的存储实现（Windows Credential Manager 或当前用户 DPAPI，经技术验证后确定），不以明文文件替代 macOS Keychain。可选外部服务仍需用户配置和明确授权。
8. 提供同事测试指南和可供用户检查后分享的脱敏诊断信息；不自动上传截图、令牌、账号和日志。

## Technical Constraints（技术约束）

- 首先在 Windows x64 构建环境验证锁定依赖的可安装性及许可，尤其是 Python、PaddlePaddle/PaddleOCR、CPU 指令集和所需系统运行库；官方支持 Windows 不等于当前锁文件和整包已验证。
- 核心像素/结构分析安装后必须离线运行，安装期间不得临时拉取分析依赖。OCR 模型的许可、体积、路径及离线初始化单列验证；无法内置时暂停该范围确认，不暗中改成联网安装或宣传完全离线 OCR。
- 普通用户账户安装；不得静默提权、关闭 Defender/SmartScreen、更改浏览器安全策略或覆盖未知 Native 注册。系统策略阻止时提供可理解提示并记录为未通过项。
- Windows Native stdio 必须使用正确的二进制帧协议，无启动日志污染 stdout；进程创建、路径包含空格/中文、文件锁和退出行为均需 Windows 实测，不能沿用 POSIX 信号假设。
- macOS chmod 模式不能作为 Windows 私有文件权限的证明；数据、凭据和状态文件需当前用户访问边界及对应测试。
- 新包按平台列出架构、版本、系统要求、哈希及扩展对应关系；不覆盖旧 v0.0.1 Release。数值扩展版本与 beta 发布标签建立对应。
- 当前未确认具备 Windows 代码签名证书。不得将开发包标为已签名或保证无安全提示；签名、信任提示及普通用户可安装性是单独交付门槛。购买证书或最终外部分发需要用户另行确认。
- Windows 自动构建/回归在 Windows 环境执行；当前 Mac 上的通过结果不能替代 Windows 真机结果。不能将 CI 沙箱环境等同于普通 Windows 11 用户电脑。
- 每阶段实现后，先进行对抗式审查，再运行测试。首次真实电脑安装、注册及凭据操作由测试人员明确同意后执行。

## Non-goals（明确不做）

- 不支持 Windows 10、Windows ARM、Edge/Firefox、企业集中部署或全机器安装。
- 不改为云端分析，不新增账号、遥测、开机自启、后台自动升级或付费系统。
- 不重做整体 UI、评分算法及完整国际化；保留现有界面，首轮优先验证 1920×1080，并检查常见 Windows 显示缩放。
- 本 SPEC 确认不授权购买证书、提交 Chrome 商店审核、公开发布 Release，或更改同事安全设置。

## Success Criteria（成功标准）

- [ ] Windows x64 CI 可从锁定依赖构建安装包，基本回归、包体内容/许可/凭据泄露检查通过；Mac 回归不倒退。
- [ ] 未装开发环境的 Windows 11 x64 真机，以当前用户完成安装，无终端/手填令牌/管理员提权；记录 OS、CPU、Chrome、包哈希及实际安全提示。
- [ ] 实际 Chrome 工具栏：启动 → 视口/整页采集 → 最近采集 → 分析 → 标注/对比 → PNG/Markdown/JSON 导出，连续 20 次无崩溃、重复提交或错误页面上传。
- [ ] 取消、导航、切页、关闭弹窗、调整窗口、中文路径、100%/125%/150% 显示缩放均有明确结果，恢复被采集页面状态。
- [ ] 实际等待空闲退出后可再次启动；后台工作台不误退出，睡眠恢复和重启后能重新配对。
- [ ] 错误 ID、旧令牌、重放票据被拒绝；未知 4179 进程和注册不被接管；并发启动只有一个服务。
- [ ] 安装/升级/修复/失败恢复/卸载不丢项目和凭据，不删除无关文件、不误杀进程；磁盘不足/文件占用有清晰失败路径。
- [ ] 安装后断网仍可完成核心分析。OCR 是否通过离线模型验收单独记录；外部 AI/Figma 的可选性和隐私文案准确。
- [ ] 同事按图文说明独立完成流程并反馈；未通过项阻断“Windows 已支持”的宣传与发布。

## 执行顺序与停点

1. 技术验证：Windows 依赖/CPU、进程协议、受保护凭据存储与图形安装工具可行性；失败先报告，不绕过锁定依赖或削减功能。
2. 平台适配、完整打包、Windows CI 与 Mac 回归；每阶段对抗式检查后测试。
3. 构建标为开发内测的候选包，核对签名/安全提示处理路径；经用户确认后提供给同事。
4. 真机验收、修复并记录证据；完成后另行决定 GitHub 预发布及商店更新。
